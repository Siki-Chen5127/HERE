## 1. 背景与问题定义

### 1.1 产品方向调整

此前原型围绕定位、报平安、紧急联系人、长辈模式及 AI 对话展开，首页主要呈现地图和安全操作。新方向将核心服务对象收敛为高校学生，核心任务调整为：表达困扰、了解自己的近期状态、连接校园支持、知道求助后续。

定位和报平安保留为辅助能力，不再作为默认首页的核心。长辈模式和独居老人照护不纳入本期新流程。

### 1.2 已知事实与待验证假设

| 类型       | 内容                                    | 依据或验证办法                       |
| -------- | ------------------------------------- | ----------------------------- |
| 项目事实     | 已有手机端、后端和网页管理端原型；已有登录、个人资料、AI 对话等代码   | 当前项目与本轮讨论；具体可用程度需另行联调验收       |
| 项目事实     | 开发环境仍依赖电脑服务及网络配置，发生过连接失败              | 本轮开发反馈                        |
| 项目事实     | 学生端存在名称显示、样式不统一、文字遮挡等问题；聊天持久化尚未完成实机验收 | 本轮反馈及代码检查                     |
| 待验证假设 H1 | 部分学生愿意先与 AI 整理困扰，再决定是否寻求人工帮助          | 访谈学生，并观察任务操作                  |
| 待验证假设 H2 | 明确说明信息共享范围，可以减少学生对学校端查看隐私的顾虑          | 比较不同说明方案的理解程度及使用意愿            |
| 待验证假设 H3 | 展示接收人和处理进度，可以减少提交求助后的不确定感             | 试点访谈与流程数据                     |
| 待验证假设 H4 | 校内存在愿意参与、有服务时间且能持续跟进的工作人员             | 与心理中心及相关部门确认，不以“已有管理后台”代替业务确认 |

### 1.3 本期要解决的问题

1. 学生有困扰时，缺少一个容易开始、可以控制隐私的表达入口。
2. 学生想找人帮助时，不清楚校内有哪些资源、如何联系、是否有人接收。
3. 提交求助后，学生和接收人员之间缺少清楚的状态反馈。
4. 原型的连接、记录保存和页面一致性不足，会影响上述任务能否完成。

这些是本期的问题假设，不代表已经证明了市场需求。

## 2. 目标与成功标准

### 2.1 本期目标

- 学生能够完成一次有效交流，退出后重新进入仍可查看已保存内容。
- 学生能够自愿记录日常状态，并查看自己的记录。
- 学生能够找到经过核验的校园资源，或主动向试点服务团队发起求助。
- 工作人员能够接收、回复和持续跟进请求，学生能够看见后续。
- 每项信息共享都有明确对象和范围，普通 AI 聊天不默认开放给学校工作人员。

### 2.2 不纳入本期

- AI 诊断、处方、治疗或“替代心理咨询师”的服务承诺。
- 依据一次发言、未签到或位置自动给学生贴心理问题标签。
- 将 AI 判定直接用于学生处分、学业评价或自动联系家长。
- 全量聊天向辅导员开放、全校学生风险排名、强制每日打卡。
- 手环生理信号、跌倒识别、自动救援、全天候无人值守监控。
- 自研或微调专业模型、跨学校部署、短信验证码完整接入。
- 本期之前的原型功能，不因仍有代码就自动成为本期正式服务。

### 2.3 建议试点观察指标

以下为讨论用目标，需先建立基线，再由团队批准；不把聊天时长、消息数量或“风险识别人数”作为主要成功指标。

| 指标          | 定义及统计口径                                      | 建议判定方式                   |
| ----------- | -------------------------------------------- | ------------------------ |
| 核心任务完成率     | 可用性测试中，无他人代操作完成指定任务的人数 / 实际参与人数；分别统计聊天、记录、求助 | 每项 ≥ 80%；样本数与失败原因一并报告    |
| 聊天恢复通过率     | 同账号返回页面、冷启动、重新登录等规定场景中，恢复已确认保存消息的通过次数 / 测试次数 | 上线验收用例全部通过               |
| 求助首次人工回应达标率 | 约定服务时限内收到首条人工回应的有效请求数 / 应在统计周期内回应的有效请求数      | 试点目标待服务团队确认；系统自动回执不算人工回应 |
| 无负责人逾期请求数   | 超过团队约定分派时限、仍无人负责的有效请求数                       | 目标为 0；需报告总请求量和服务时段       |
| 交流帮助感       | 自愿反馈中选择“有一点帮助/有帮助”的有效反馈数 / 有效反馈数             | 先建立基线；同时报告反馈人数与反馈率       |
| 隐私理解度       | 测试者能否正确回答“老师能看到哪些内容”“如何删除聊天”                 | 所有关键误解均需修正后复测            |

## 3. 用户与使用场景

### 3.1 用户角色

| 角色     | 主要任务                  | 默认可见范围                     |
| ------ | --------------------- | -------------------------- |
| 学生     | 交流、记录状态、查看资源、提交和跟进求助  | 本人数据及本人请求                  |
| 服务受理人员 | 查看待受理请求、分派负责人、监督未处理请求 | 所属服务团队的请求及必要联系信息           |
| 跟进人员   | 回复学生、记录跟进、安排下一步、结束或转介 | 分派给本人的请求及学生授权分享的内容         |
| 系统管理员  | 配置账号、权限、资源、服务时段       | 系统配置和审计信息；管理身份不默认附带聊天内容访问权 |

“跟进人员”由学校指定并明确职责；辅导员与心理专业人员的职责不自动等同。同一人可兼任多个角色，但需显式授权。

### 3.2 核心场景

**场景 A：考试压力下的日常交流。** 学生晚上感到疲惫，打开应用表达困扰；AI 帮助整理想法、提供可选择的小步骤。学生第二天可以接着原会话交流，或自行开启新会话。

**场景 B：回顾近期状态。** 学生自愿记录“今天有些累”，附上一句说明。一周后回顾记录，了解当时发生了什么；不被系统据此生成诊断或强制上报。

**场景 C：希望有人帮助。** 学生从聊天或资源页发起求助，先查看接收团队、服务时间和分享内容；确认提交后，查看接收与回复进度。

**场景 D：暂时无法等待。** 学生明确表示需要立即帮助，页面提供可直接使用的紧急联系入口及学校核验的紧急渠道。普通求助队列不承诺即时响应。

## 5. 信息架构与设计要求

### 5.1 学生端建议结构

底部导航建议为“首页、聊天、记录、我的”，待原型测试确认。

- 首页：昵称、简短问候、聊一聊、记录状态、校园帮助、进行中的求助；紧急帮助保持容易找到。
- 聊天：历史会话、新对话、当前对话；不会默认显示他人聊天。
- 记录：本人的状态历史；可以进入求助进度。
- 我的：个人资料、学校绑定、数据与隐私、联系人、设置、退出登录。
- 二级页面：资源详情、求助提交、求助详情、共享预览与数据管理。

### 5.2 视觉与交互原则

1. 浅色中性背景、低饱和绿色为主色；红色只强调紧急或破坏性操作。
2. 普通正文建议 16，行高随字体同步调整；字号为设计参考值，需结合真机测试。
3. 不依赖固定文字容器高度；在系统默认及 1.5 倍字体下验证关键任务不遮挡，长名称可换行或合理截断。
4. 返回、提交、取消的位置和用词保持一致；关键按钮可触区域至少 48×48 dp。
5. 地图退出首页主视觉，不用呼吸光圈、玻璃卡片或大面积阴影承载普通内容。
6. 状态文字必须反映实际情况；未验证连接时不显示“在线”，未收到人工回复时不显示“老师已处理”。
7. 轻量成功反馈采用页面提示；删除、分享、撤回等需要用户明确决策的操作才使用确认流程。

## 6. 核心流程

### 6.1 首次使用

首次打开 → 了解服务及数据范围 → 登录或注册 → 设置昵称 → 进入首页。

一般交流和状态记录不强制索取定位、通讯录或学校身份。连接具体学校的人工服务前，按试点规则验证学校归属；推荐采用学校邀请或校内认证，具体方式待确认。尚无短信能力时，不把“填写了手机号”当成“已经验证号码归属”。

### 6.2 从聊天到人工帮助

交流 → 学生点击“联系校园支持” → 选择有效服务团队 → 填写说明和可用联系时间 → 可选分享聊天片段/状态记录 → 预览最终内容 → 确认提交 → 获取请求编号 → 查看进度与回复。

默认不附带完整聊天、位置、健康档案；AI 生成的求助摘要必须先由学生检查、编辑和确认。

### 6.3 工作台闭环

请求到达 → 服务团队受理/分派 → 负责人首条人工回复 → 双方继续沟通 → 形成下一步安排 → 确认结束、撤回或转介 → 保留必要的流程记录。

已有后台的工单字段和角色可以评估复用，但必须用新的学生求助流程验收，不能只检查“后台出现了一条记录”。

## 7. 详细功能与验收标准

### F01 账号资料与昵称

用户故事：作为学生，我希望各页面使用同一个昵称，不把完整手机号当成首页名称。

规则：昵称与实名信息分开定义；学生端优先展示昵称，未设置时显示“同学”并提供设置入口。“我的”中手机号脱敏展示。修改昵称后同步刷新本人相关页面。实名认证或学校归属信息另行处理，不直接替代昵称。

验收：修改昵称后返回首页立即显示新值；重启仍保持；长昵称不遮挡操作；账号 A 的资料不会出现在账号 B。

### F03 AI 对话与历史

用户故事：作为学生，我希望能接着之前的话题交流，也能主动开始一段独立对话。

**规则：**

- 每段会话有独立标识、标题和时间；会话内容按当前账号隔离。
- 本期目标为服务端保存会话，并提供本机缓存；升级前的本地记录可保留在原设备并明确标识，不默认上传旧记录。
- 区分“发送中、已保存、回复中、失败”；仅在服务端确认后显示“已保存”。断网草稿明确标记“仅在本机”，不能承诺已同步。
- 离开页面不等于丢弃已经受理的生成任务；重进页面可查询其结果或明确失败状态。完全离线时不承诺继续生成。
- 重试不重复创建同一条学生消息；发送失败保留原文和重试入口。
- 同一会话的后续请求带上规定范围的历史上下文。超出上下文窗口时不保证记住全部旧内容，具体截断/摘要策略由研发给出并纳入测试。
- 新对话不自动注入其他会话内容。跨会话偏好记忆属于 F11，需单独开关。
- 思考内容为模型可选返回字段，有则折叠展示，无则隐藏；不把思考内容当作诊断或可靠性证明。
- 提供删除当前会话；删除后不再用于后续上下文，界面也不恢复该会话。

**验收：**

1. 同账号返回页面、冷启动及重新登录，已保存消息完整恢复；第二设备联网后可读取服务端会话。
2. A 登出后 B 登录，列表、缓存和未完成请求结果均不串号。
3. 发送时断网、生成中离开、重复点击重试分别有明确结果，不丢原文、不重复入库。
4. 删除会话后重启及另一设备刷新均不再显示；后台后续请求不携带该会话。
5. 构造短对话后提问其中已出现的信息，确认请求确实带上对应上下文；不以模型偶然猜对代替验证。

### F04 日常状态记录

规则：一天可保留一条日常记录并允许修改。状态建议为“很好、还不错、一般、有些难受、很难受”，可选添加不超过 500 字说明。可以跳过、不连续提醒，不使用断签惩罚。

列表显示日期、本人选择的状态和备注。暂不输出“抑郁风险”“健康分”等结论。学校端默认不可见，学生发起求助时可选择具体日期分享。

验收：新增、编辑、删除后重启结果一致；跨设备并发编辑时提示版本冲突，不静默覆盖；未授权的工作人员无法查询记录正文。

### F05 校园支持资源

规则：展示所属学校的服务团队、服务范围、工作时间、联系方式、地点或预约链接，以及最近核验日期。每项资源指定维护人；失效资源下架或标记不可用。

验收：号码/链接由学校确认；可拨号或打开有效预约页；非服务时段如实提示；无可用资源时不显示虚构人员或空白预约页。

### F06 求助提交与共享

**规则：**

- 需学校归属验证及已启用的接收团队；未接入学校时可使用公开资源，不出现假提交成功。
- 必填为接收团队、求助说明及至少一种团队可使用的联系途径；已验证的站内账号可作为途径，不强迫公开手机号。
- 可选填写方便联系的时间；可选附上本人挑选的聊天片段或状态记录。
- 确认页列出“谁会收到、会看到什么、服务时间、预计回应规则”。
- 使用防重复提交标识。仅在请求和分享快照被服务端保存后返回成功及请求编号。
- 分享内容保存为提交时的快照；不会因工作人员打开请求而自动获取学生后来新增的聊天。

验收：取消分享不产生请求；重复点击仅生成一条；连接失败不显示提交成功；后台实际可见内容与学生预览一致。

### F07/F08 受理、跟进与进度

| 状态     | 含义             | 允许的主要变化                 | 学生可见内容                       |
| ------ | -------------- | ----------------------- | ---------------------------- |
| 待受理    | 服务端已保存，尚无人工受理  | 处理中、已撤回                 | 提交时间、接收团队、服务时段               |
| 处理中    | 已有负责人并开始处理     | 等待学生回复、已结束、已转介、已撤回      | 人工回复、负责人对外称呼、下一步安排           |
| 等待学生回复 | 工作人员提出需学生回应的问题 | 处理中、已结束、已撤回             | 待回复内容；不因暂未回复而自动判定危险          |
| 已转介    | 已记录转向其他服务的安排   | 按本团队流程结束；需要继续跟进时仍保留后续任务 | 去向、联系方法、下一步；区分“建议转介”和“已确认接收” |
| 已结束    | 本次流程结束         | 可发起关联的新请求               | 结束原因、公开总结、后续求助入口             |
| 已撤回    | 学生终止本次请求       | 可重新发起                   | 撤回时间及必要说明                    |

**补充规则：**

- 只有授权人员可以受理和分派，跨团队、跨学校不得越权访问。
- 状态变化留存操作人和时间；学生可见回复与内部工作备注分开存储、分开授权。
- 自动回执仅表示“提交成功”；首条人工回复是独立事件。
- 回应时限按学校确认的服务日历计算，非工作时段明确展示；逾期提醒指定的值班/协调负责人。
- 学生可以撤回；受理后撤回通知负责人并停止常规后续任务。撤回不等于抹去已依法/依约保留的必要流程记录，具体规则需提前确定。
- 转介不是点一下即完成：需记录去向和接收状态，不能把“提供电话号码”显示成“已预约成功”。
- 本期至少有应用内未读和详情时间线；未接入可靠推送时，告知学生需再次打开应用查看，不能承诺锁屏通知。

验收：从学生提交到人工回应、往返交流、结束完整走通；未授权角色无法修改状态；两人同时分派不会产生两个有效负责人；逾期提醒、撤回、转介和非服务时段分别有测试用例。

### F09 隐私、分享与删除

| 数据      | 默认谁能看          | 如何分享或使用                       | 删除/保留要求              |
| ------- | -------------- | ----------------------------- | -------------------- |
| 私人会话    | 本人；服务端仅按授权处理   | 明确说明将发送给模型供应方的上下文范围；学校人员不默认查看 | 本人可删除；停止后续引用         |
| 状态记录    | 本人             | 学生选择具体记录后附入请求                 | 本人可删除；已分享快照按请求规则处理   |
| 请求及分享快照 | 本人和有权限的受理/跟进人员 | 用于本次受理及必要协调                   | 保留期限、撤回影响、删除途径需试点前确认 |
| 内部工作备注  | 被授权的工作人员       | 仅作必要的服务协作                     | 保留和访问规则由学校及项目共同确认    |
| 定位      | 默认不采集          | 本期核心心理支持流程不依赖定位；紧急场景另行明确授权    | 无必要不保存               |
| 分析与运行日志 | 授权运维/分析人员      | 使用事件名、耗时、错误码等必要信息             | 不记录聊天正文、密码、Key、完整号码  |

本期不得将学生真实聊天默认用于微调、训练或人工标注。若未来需要研究或训练用途，单独设计明确的选择和退出机制。

数据删除须明确覆盖在线库、缓存及备份的处理期限，区别“立即不再展示/不再调用”与“备份到期清除”。具体天数尚待确认，是试点上线前的阻塞项；界面不得提前声称“立即彻底删除所有副本”。

验收：跨账号、跨学校、角色越权访问均被拒绝；分享预览与实际一致；删除后不会被历史上下文重新带出；日志抽查不含正文或密钥。

## 8. 紧急场景与服务边界

本产品提供日常心理支持与求助连接，普通请求队列不等同于紧急救援。

- 首页、聊天及求助页有可到达的“需要立即帮助”入口；展示经核验的学校紧急渠道及通用紧急服务入口。
- 学生明确表达当前可能面临现实危险时，优先呈现直接联系真人的选项，不引导其继续等待常规工单。
- 对话识别仅用于提供支持入口和提醒，不能直接形成诊断、处分依据或自动向家长发送聊天。
- 需要在紧急场景下突破通常分享范围的规则，必须先由学校专业服务团队确定适用条件、人工判断、接收责任及记录要求。本期不默认实现自动外发。
- 页面不承诺“24 小时有人回复”或“必定救援成功”；若实际具备全天服务，需独立验证人员安排与渠道。

## 9. AI 质量与内容要求

本期使用现有模型完成受控试点，先评测再决定是否替换或微调。

评测案例需覆盖：考试压力、人际冲突、就业困扰、普通闲聊、明显求助、含糊表述、模型不确定的问题、虚构校内信息诱导和多轮上下文丢失。

由心理专业人员参与评审，检查：是否理解学生表达、是否强行诊断、是否虚构学校资源、是否做出无法兑现的承诺、是否在需要时提供合适的人工帮助入口。专家评审和测试通过不等同于已经证明临床疗效。

已核验的学校资源从可更新资源库获取；资源库没有的人员、电话、预约名额，不允许模型编造。模型升级前复测同一组案例，记录版本、问题及处理结果。

## 10. 数据对象与接口协作范围

PRD 规定业务含义和行为，不代替研发的数据库与接口设计。

| 对象      | 主要业务字段                            |
| ------- | --------------------------------- |
| 学生资料    | 账号标识、昵称、学校归属及验证状态、偏好              |
| 会话/消息   | 所属账号、会话标识、角色、正文、时间、发送/生成状态、保存状态   |
| 状态记录    | 所属账号、本地日期、状态、备注、修改版本              |
| 校园资源    | 学校、团队、范围、渠道、服务时段、核验时间、维护人、启用状态    |
| 求助请求    | 编号、学校、接收团队、说明、联系途径、负责人、状态、时间、分享快照 |
| 回复与流程事件 | 请求编号、操作者、事件类型、公开/内部范围、时间、内容       |
| 共享记录    | 分享对象、确认范围、版本和时间、撤回或变更记录           |

服务端需统一账号标识、检查对象归属、支持重复提交保护和并发状态校验。前端隐藏按钮不代替服务端权限校验。

旧版存储中的姓名、手机号、本地用户标识与后端账号标识需做映射审查；不根据“最后一条用户记录”选择数据归属。迁移规则由研发提供方案，再逐项验收。

## 11. 运行质量与异常处理

| 场景          | 期望行为                                       |
| ----------- | ------------------------------------------ |
| 后端不可达       | 页面明确提示连接失败，保留未提交输入，提供重试；不显示“网络波动”后伪造 AI 回答 |
| 登录过期        | 引导重新登录，避免将未提交草稿绑定到另一账号                     |
| AI 超时或供应方失败 | 结束等待、保留学生消息、显示重试；已生成且保存的结果重进后可查            |
| 工作台服务关闭     | 停止接收新请求并展示替代渠道；已有请求有指定负责人处理                |
| 资源过期        | 维护人员收到核验任务，学生端下架不可用入口                      |
| 数据同步失败      | 明确区分仅本机、待同步、已保存，重连不重复创建                    |
| 存储读取失败      | 显示恢复失败并保留原始记录，不用欢迎语覆盖旧数据                   |

建议性能基线：在约定的试点网络、设备和并发条件下，普通业务接口 P95 ≤ 2 秒；AI 回复单独统计首反馈和完成耗时，不计入普通接口口径。设备、并发量及超时阈值由研发评估后确认。

试点需要独立部署的服务、备份及恢复演练；不能要求使用者连接开发者电脑。监控至少覆盖健康状态、请求错误、生成失败及无人接收请求。

## 13. 验收与发布条件

### 13.1 必须通过的端到端验收

- [ ] 账号资料统一，默认/大字体及长内容不遮挡主要操作。
- [ ] 对话保存、恢复、删除、换号隔离、生成中离开及错误重试全部通过。
- [ ] 状态记录新增、编辑、删除及私密性通过。
- [ ] 资源真实可用，维护责任明确。
- [ ] 学生提交 → 后台接收 → 人工回复 → 学生查看 → 结束/撤回/转介走通。
- [ ] 权限越权、重复提交、并发分派、断网及登录过期场景通过。
- [ ] 非服务时段与紧急入口提示经过业务/专业负责人确认。
- [ ] 专业评测无未解决的阻断问题。
- [ ] 云端部署、备份恢复和关键运行监测完成。

### 13.2 上线前必须确定的业务依赖

| 依赖                      | 未满足时的处理           |
| ----------------------- | ----------------- |
| 学校同意参与、学生自愿参加及具体试点范围    | 不发布校级服务承诺；可先做内部演示 |
| 接收团队、负责人、服务时段、分派及人工回应时限 | 不开放可提交的人工求助入口     |
| 学校归属验证与工作人员身份授权         | 不启用真实学生请求分派       |
| 资源核验及紧急情况处理职责           | 不宣称已具备学校服务保障      |
| 数据共享、保存期限、撤回、删除与备份规则    | 不开始真实敏感数据试点       |
| 模型处理数据范围及供应方条款审核        | 不上传真实学生聊天用于试点     |

### 13.3 发布与暂停

先做内部测试，再做单校自愿试点；不直接全校强制推广。若发生跨账号数据可见、错误外发、无人接收请求或严重误导内容，暂停对应入口，处理未完成请求并通知相关受影响用户。保留关闭新请求、切换资源页和回退版本的能力。

## 16. 如何把本文用于实际工作

1. 产品说明背景与目标，参会人先确认要解决的问题和范围。
2. 设计用第 5—7 节绘制页面及交互状态；展示完整流程，不能只有几张静态首页。
3. 研发检查数据来源、状态转换、权限、异常和依赖，给出技术方案及估算。
4. 测试把“规则”和“验收”转成用例；例如把 F03 拆成恢复、换号、删除、断网和重试用例。
5. 学校业务方确认接收、分派、回应和转介规则；专业人员参与 AI 内容及紧急场景评审。
6. 产品根据结论修订版本，明确本期做与不做，再排期。

**示例追踪关系：**问题“退出后不能接着聊” → 目标“已保存对话可恢复” → 需求 F03 → 会话/消息数据与接口方案 → 冷启动恢复测试 → chat_restore_result 指标。

PRD 的结构可以因团队而不同。更重要的是需求可追踪、规则无歧义、边界可执行、结果可验收。
